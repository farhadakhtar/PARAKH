# Calibration dataset - build report

Generated by `tools/build_calibration_dataset.py`. Read-only over `Data/`; no PARAKH module was imported or modified.

## Verdict

**Targets met on paper. The dataset is NOT calibration-ready.**

5,237 records carry a label, which clears the 200 threshold. Three separate facts stop it being usable, and any one of them alone would be enough:

1. **One class only.** 5,237 positive, 0 negative. A calibration curve maps a score to an observed rate; with nothing to contrast against there is no rate to observe. This is not a small-sample problem - it is the absence of the second axis.
2. **No features on the labelled rows.** 0 of 5,237 carry a budget or expenditure figure, so there is no score to calibrate against the label.
3. **The labels landed on the wrong kind of record.** 99.0% of them are rows from `5c2f62fe-5afa-4119-a499-fec9d604d5bd.csv`. A finding in a CAG report does not make a row in that file an instance of the irregularity - the two share a district, nothing more.

The labels are retained rather than suppressed so the alignment can be inspected, but nothing should be fitted on them.

## What was deliberately not done

**The ground-truth ledger was not used as labels.** It records injected *data-quality* noise - `missing:vendor_name`, `placeholder:date_approval`, `date_order:approval_before_proposal`. None of those is an overpayment, a ghost beneficiary or a procurement irregularity, so mapping them onto audit categories would be fabrication. The ledger's own note also states: *"NEVER join this into the corpus before Stage 7 evaluation - it leaks labels."*

**No rows were invented to reach the label target.** Every label traces to a paragraph in a real audit PDF, listed in `audit_labels.csv` by page.

**Synthetic records were never labelled.** `synthetic_dataset.csv` is excluded by rule rather than by coincidence: a real audit finding cannot confirm or clear a fictional work.

## Why the labels are unusable - the measurement

The cause is coverage, not a parsing defect. Two disjoint sets:

- audit reports cover **DELHI, JAMMU AND KASHMIR, JHARKHAND, NAGALAND**
- the only real records carrying a budget or expenditure figure (396 rows, from `ee03643a-...csv`) cover **RAJASTHAN**

Intersection: **empty**. No join on state can put a label on a record that has a feature, so the matcher fell through to the one remaining large file with district names - a postal directory. It matched geography because that is all it was given to match on.

The parser is working. It read 70 observations across 3 report(s), with issue type, severity, district and rupee amounts. The gap is on the structured side.

## What would actually close the gap

Not more audit PDFs. Structured public-works financial data - scheme, district, year, sanctioned amount, expenditure - for the **same states the audit reports cover** (DELHI, JAMMU AND KASHMIR, JHARKHAND, NAGALAND). MPLADS/MPLADS-style work registers, state PWD expenditure statements, or scheme-wise district releases.

Two further conditions must hold before anything is fitted:

1. **Negatives must exist.** A district-year an audit examined and did not fault is a negative. That requires knowing an audit's *scope*, not only its findings - which paragraphs cover which units. Without scope, absence of a finding is indistinguishable from absence of an audit, and only NULL is honest.
2. **The match must be narrower than a district.** State + district + year is a weak label: it says an irregularity occurred somewhere in that district that year, not that this work is the irregularity.

PARAKH's Stage 8 requires `provenance='real'` and refuses anything else. On this dataset it should continue to refuse, and does.
