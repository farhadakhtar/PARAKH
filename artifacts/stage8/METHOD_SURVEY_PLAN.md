Ranked implementation order\n\nRanked by value per unit of effort. The "adds beyond" column is the load-bearing justification — if a detector's signal is recoverable from the built z-scores, HHI, peer clusters or duplicate detection, it is cancelled in §5 instead.\n\n### R1 — Contract-splitting / fragmentation scan\n**Effort: 2–3 days. Value: HIGH. Build first.**\n\nAdds beyond existing: near-duplicate detection (`src/stage3/duplicate_detection.py:103`) finds records that are *the same work recorded twice* — high cosine, same district, temporally close. Splitting is the opposite polarity: works that are **deliberately distinct** in name, awarded by one agency in one window, each priced below a delegation threshold, summing above it. The duplicate detector's own threshold *rejects* exactly the pairs this looks for. Cost z-scores cannot see it either — each fragment is individually unremarkable against its peer cell; the anomaly exists only in the *sum*, an object no built component forms. HHI sees vendor share, not award fragmentation.\n\n### R2 — Threshold-bunching and terminal-digit preference on sanction amounts\n**Effort: 1–2 days. Value: MEDIUM-HIGH, but zero yield until real data. Build second because it is cheap and shares R1's threshold ladder.**\n\nAdds beyond existing: z-scores measure *magnitude* against peers. This measures whether an amount was **constructed rather than estimated** — mass piling just below an administrative figure, or digit preference indicating back-fitted numbers. A sanction of ₹24.6 lakh is perfectly normal on every built z-score and is the entire signal here. The compliance engine (`src/stage8/compliance.py`, `OPEN_TENDER_THRESHOLD_INR`) already *cites* the ₹25 lakh threshold, but evaluates it per-record as a rule needing `procurement_method`, which the corpus does not have. A density test needs no such column.\n\n### R3 — Agency-versus-its-own-history drift\n**Effort: 2 days. Value: MEDIUM-HIGH. This is the review's own RRP salvage note, and it is correct.**\n\nAdds beyond existing: verified in code — every PARAKH z-score is peer-relative, and the peer key carries no agency and no time. An implementing agency whose cost profile shifts sharply against **its own** two-year history is invisible to peer z-scores **if its whole peer cell drifted together** — which is exactly what a scheme-wide rate revision, or a coordinated inflation across one agency's book, looks like. Different question, different null hypothesis.\n\n### R4 — Vendor award-order rotation within an agency\n**Effort: 2 days. Value: MEDIUM, high false-positive risk. Build fourth, and gate it hard.**\n\nAdds beyond existing: HHI is a function of *shares only*. A trio of vendors rotating strictly A-B-C-A-B-C and a trio winning at random with identical shares have **identical HHI**. Order carries information that concentration discards. The review correctly cancelled vendor-agency *pairing* as HHI-covered; sequence is a different object.\n\nThe honest caveat, which must ship with the output: this is **not** the Wachs–Kertész co-bidding screen and cannot distinguish a rotating cartel from two firms serving different blocks of one district on alternating schedules. Route as a lead requiring corroboration, never as a finding.\n\n### R5 — External expenditure reconciliation harness\n**Effort: 1 day for the harness. Value: HIGHEST on acquisition day, ZERO before it. Build last, ship dark.**\n\nAdds beyond existing: it is the only proposed check that produces a **deterministic contradiction** rather than a relative outlier — "this district's recorded spend exceeds the money released to it" needs no peer group, no norm, and no label. The review is right that this is an acquisition task, not a modelling one. Build the adapter now so the check is live the hour the data lands.\n\n---\n\n## 2. Per-detector specification\n\n### R1 — Contract-splitting / fragmentation scan\n\n**Columns:** `work_id`, `implementing_agency`, `district`, `sanction_amount`, `date_approval` (fallback `date_proposal`), plus `cluster_id` and the TF-IDF `record_vectors` already produced by Stage 3, plus `duplicate_group_id` as an exclusion mask.\n\n**Grouping key:** `(normalised implementing_agency, district, cluster_id)`, ordered within group by `date_approval`.\n\n**Threshold ladder `T`:** a table of `(state, effective_from, threshold_inr, citation)`. Do **not** hard-code ₹25 lakh alone — measured, only 5.9% of dev-corpus amounts reach it, so a single-threshold test has near-zero coverage. Delegation-of-financial-power figures vary by state and year and must be cited per row like every other statutory constant in `src/stage8/compliance.py`.\n\n**Tiered architecture:**\n\n- *Cheap screen — sorted scan + two-pointer sliding window.* One `sort` on `(key, date_approval)`: **O(n log n)**, one pass thereafter. A two-pointer window of `W` days carries a running sum and a running max. Emit a candidate when `count ≥ 2` **and** `running_max < T` **and** `running_sum ≥ T`. Memory is **O(window)**, not O(n) — this is what makes it run at 1M rows.\n- *Early exit* — four gates, in this order, cheapest first:\n  1. Skip the entire key-group if `max(sanction) ≥ T` — if one work already crosses the threshold, nothing was split to avoid it.\n  2. Skip if group `count < 2`.\n  3. Skip if the **whole key-group's** sum `< T` — one comparison kills most groups before the window ever runs.\n  4. Drop members sharing a `duplicate_group_id` — those are duplicates, a different finding, already reported by Stage 3.\n- *Expensive check — pairwise, inside surviving windows only.* Reuse the Stage 3 TF-IDF rows (do **not** re-vectorise) to confirm the members are genuinely *distinct* works: cosine **below** `DUPLICATE_SIMILARITY_THRESHOLD` (else it is a duplicate) and above a coherence floor (else it is an unrelated coincidence). Cap group size at 12 and skip the C(n,2) expansion beyond that — a 40-work window is a busy agency, not a split. Cost is **O(Σ c²)** over candidate windows only, with c ≤ 12.\n\n**Data structures:** sorted array + two pointers; union-find (the `_UnionFind` at `src/stage3/duplicate_detection.py:81` is reusable) to merge overlapping windows into one fragmentation set.\n\n**Output contract:** the member `work_id` list, the summed total, the threshold and its citation, and the gap to threshold. The verification note must state: *without `procurement_method` we observe a pattern consistent with threshold avoidance; we cannot establish that a tender was avoided.*\n\n---\n\n### R2 — Threshold-bunching and terminal-digit preference\n\n**Columns:** `sanction_amount`, `implementing_agency`, `state`, `date_approval`.\n**Grouping key:** `state` for the density test; `implementing_agency` for the digit test.\n\n**Tiered architecture:**\n\n- *Cheap screen — fixed-bin histogram.* Clip to the 0.1–99.9 percentile first (the raw column contains `1e300` and `1.2e400`; unclipped `bincount` over that range is an OOM, not a histogram). Bin at ₹1,000 into an `int64` array via `np.bincount`: **O(n)** time, memory bounded by the clipped range, ~10k slots. Compute, at each candidate round figure in {1L, 2.5L, 5L, 10L, 25L, 50L, 1Cr}, the ratio of mass in `[T−δ, T)` to `[T, T+δ)`.\n- *Early exit:* a threshold with fewer than N records inside `T ± 20%` yields **undefined**, never a weak score. Agencies with < 50 usable amounts get no digit test at all.\n- *Expensive check:* bootstrap the below/above ratio per `(state, agency)` for surviving thresholds only — resampling is the only costly part and it touches a handful of cells.\n- *Digit test:* a lazily-allocated 1,000-slot `int64` array per agency (only for the ~288 agencies clearing 50 rows), chi-square against uniform on the last three digits. **O(agencies × 1000)**.\n\n**Validation, stated plainly:** measured, 0.09% of dev-corpus amounts end in `00000`. This detector will find nothing on the synthetic corpus, and that is the correct result, not a bug. Validate mechanics by adding a bunching channel to the injection ledger (`data/ground_truth_ledger.json`, vectorised through `src/stage8/injection.py`) — noting that injected defects validate *machinery*, not fraud detection, since an injected defect is not a fraud label.\n\n---\n\n### R3 — Agency-versus-its-own-history drift\n\n**Columns:** `implementing_agency`, `sanction_amount`, `amount_spent`, `date_approval`, `date_completion`, `work_id`. Reuse the three Stage 3 fields directly: `log_cost`, `spend_ratio`, `duration_days` (`PEER_STAT_FIELDS`, `src/stage3/peer_cells.py:56`).\n\n**Grouping key:** `implementing_agency` **pooled across years** — not agency-year. Measured: agency-year gives median 2 rows per cell; agency alone gives median 19 with 288 cells ≥ 20. Split each agency's own records into a reference window (everything but the trailing 12 months) and a test window (trailing 12 months).\n\n**Metric:** robust location shift per field, `(median_test − median_ref) / (1.4826 × MAD_ref)`, plus a Mann-Whitney U on the two windows. Report `n` on each side alongside the statistic — a shift computed on 13 rows is a different object from one on 400 and the artifact must not conflate them.\n\n**Tiered architecture:**\n\n- *Cheap screen — two-heap streaming median.* Max-heap of the lower half, min-heap of the upper half, per agency, in a single date-sorted pass: **O(n log k)** with k the agency's row count, memory O(k) for the active agency only. At 20k rows a plain groupby is fine; the two-heap version is what survives 1M rows without materialising per-agency frames.\n- *Early exit:* `min(n_ref, n_test) < 12` → **UNDEFINED**, emitted as such. Never impute, never score a thin cell.\n- *Expensive check:* a within-agency permutation test (shuffle the time labels, 500 reps) only for agencies whose cheap shift exceeds 2.0 **and** clear 20 rows on both sides. Expect on the order of 100–200 testable agencies at dev scale — an estimate to be measured on the first run, not a promise.\n\n**Why it is not a duplicate signal:** confirmed by reading `form_peer_cells`. The peer key is `(cluster_id, cost_stratum)`. A z-score asks "is this work unusual among works like it?"; this asks "is this office behaving unlike itself?". Cells drifting together defeats the first question and not the second.\n\n---\n\n### R4 — Vendor award-order rotation\n\n**Columns:** `implementing_agency`, `vendor_name`, `district`, `date_approval`, `work_id`.\n**Grouping key:** `(implementing_agency)`, sequence ordered by `date_approval`; secondary run at `(implementing_agency, district)`.\n\n**Vendor normalisation — the constraint that shapes this detector:** use **exact equality on a conservatively normalised string only** (case-fold, collapse whitespace, strip the trailing `(Unit N)` variants visible in the raw data, drop the `NULL`/`N/A`/`unknown` sentinels). Do **not** fuzzy-cluster vendor names. The ARACHNE note is right: with no PAN/CIN and code-mixed Hindi/English strings, a fuzzy matcher degrades badly, and a false vendor merge here manufactures a rotation pattern that does not exist. 529 distinct vendor strings at dev scale; record the normalisation rules as a caveat on every output.\n\n**Tiered architecture:**\n\n- *Cheap screen — one pass, adjacency-repeat count.* For each agency compute the observed number of adjacent same-vendor award pairs and the vendor share vector; under a share-preserving multinomial null the expected adjacency count is closed-form. A rotating group produces **significantly fewer** same-vendor adjacencies than chance. **O(n)**.\n- *Early exit:* agencies with < 30 awards, or < 3 distinct vendors, or |z| ≤ 2 → skipped entirely before any mining.\n- *Expensive check:* rolling-hash n-gram mining (n = 2..4) over the ordered vendor-id sequence, top-k retained in a **min-heap of size k**, compared against 200 share-preserving shuffles. **O(n × 4)** per pass, ~200 passes on the small survivor set.\n\n**Gate:** output routes at lead severity only, with the specialisation/geography confound named in the verification note.\n\n---\n\n### R5 — External expenditure reconciliation harness\n\n**Corpus side:** `state`, `district`, `sanction_amount`, `amount_spent`, FY derived from `date_approval` (April–March).\n**External side:** a `(state, district, financial_year) → released/reported expenditure` series.\n**Grouping key:** `(state_canonical, district_canonical, fy)`.\n\n**Algorithm:** two `groupby.sum()` calls, one left join, one subtraction. Flag (a) districts where corpus spend exceeds reported release, (b) districts whose sum exceeds their own state total. That is the whole model, and it needs no labels because it is an arithmetic contradiction.\n\n**Where the engineering actually is — the adapter contract, not the algorithm:**\n- Unit normalisation. `data\RS-Session-251-AU3186-Annexure-I.csv` is districts × FY-columns in **crore** — melt the FY columns to rows and multiply by 1e7. Every adapter declares its unit and its multiplier explicitly; a silent crore/lakh confusion is a two-order-of-magnitude false finding.\n- District canonicalisation against a controlled list (98 distinct district strings in the dev corpus, including `N/A`, `NULL` and blanks). Unmatched districts are reported as **unmatched**, never dropped silently — a dropped district is a hidden false negative.\n- FY derivation with the April–March boundary made explicit and tested.\n\n**The measured blocker, restated:** that Punjab file covers FY2017-18 to FY2019-20; the real PMGSY aggregates run FY2023-24 onward; the CAG evidence is Nagaland FY2020-21. **Every pairwise intersection is empty.** The dev corpus does contain Punjab 2017 rows (e.g. `MPL-PB-2017-000006`), so they can serve as a **golden-test fixture** for the adapter — and any residual computed from them must be stamped non-evidentiary, because joining synthetic amounts to real release figures produces a meaningless number.\n\n---\n\n## 3. Engineering hacks\n\nEvery trick surfaced by the review, plus the ones the five builds above need. This section is durable independent of which detector ships — it is what makes acquisition-day builds cheap.\n\n**Blocking and bucketing**\n- **Bucket-size cap before union-find.** When clustering entities on shared attributes, drop any attribute value shared by more than `k` entities *before* the union step. One common-services-centre IP or one generic registered-office address otherwise swallows the entire graph into a single component. The cap is the load-bearing parameter, not the union.\n- **Geohash instead of haversine.** Geohash coordinates to ~7 characters and group. Two works claiming one asset land in the same bucket, turning an O(n²) distance sweep into an **O(n) groupby**. Compute exact distances only inside buckets already holding ≥ 2 works; check the 8 neighbouring cells only for points within the cell-edge tolerance. Run point-in-polygon only for records whose tile straddles a boundary.\n- **Reuse existing blocks.** Stage 3 already blocks on `cluster_id` and district and already holds the TF-IDF matrix. R1 rides both. Never re-vectorise.\n\n**Sort orders and scans**\n- **Sort once, scan many.** One `sort` on `(key, date)` amortises across R1's window scan, R3's temporal split and R4's sequence build. **O(n log n)** paid once.\n- **Two-pointer sliding window** with running sum and running max: O(n) after the sort, memory O(window).\n- **Shift-and-diff on sorted instrument numbers.** Consecutive-DD detection is a sort on `(issuing_branch, instrument_date, instrument_number)` then `diff == 1` on adjacent rows restricted to rows sharing a tender. O(n log n), one pass, no model.\n\n**Sketches and bounded memory**\n- **Two-pass heavy hitters.** Pass one accumulates sorted-pair hashes into a **Count-Min sketch** at fixed memory; pass two exact-counts only the pairs the sketch puts above threshold. This is how repeat-pair analysis runs at 1M rows in bounded RAM.\n- **Restrict pair enumeration by size.** Cap at tenders with ≤ 5 participants: C(5,2) = 10 pairs each. Given ~46% of tenders are two-bid, this loses almost nothing and bounds the blow-up.\n- **Two-heap streaming median** (max-heap low / min-heap high) for per-group robust location in one pass — O(n log k), no per-group frame materialisation.\n- **Min-heap top-k** for n-gram mining; never sort the full n-gram counter.\n- **Fixed-bin `bincount` histogram with percentile clipping.** Clip before binning — the raw amount column contains `1e300`.\n- **Lazy per-group array allocation.** Allocate the 1,000-slot digit counter only for groups that clear the minimum-n gate.\n\n**Hashing and fingerprints**\n- **Fingerprint instead of compare.** Hash an ordered rate vector (rounded to stored precision) into one 64-bit value; identical vectors collapse to one groupby key. Turns O(packages² × items) pairwise variance into **O(n) hash aggregation**. Compute conditional variance only for fingerprints that already repeat.\n- **Rolling hash over sequences** for n-gram extraction in one pass.\n\n**Early exits — the highest-leverage category**\n- **Homogeneity exit:** a `groupby(...).nunique()` on the quoted tax rate eliminates the >95% of tenders where every bidder quoted identically, before any re-ranking work.\n- **Ceiling exit:** skip a group when its max already exceeds the threshold under test (R1 gate 1).\n- **Aggregate exit:** skip when the whole group's sum is below threshold (R1 gate 3) — one comparison per group.\n- **Minimum-n exit:** emit `UNDEFINED` rather than a weak statistic (R2, R3). This is a correctness rule as much as a performance one.\n- **Materialise only co-occurring clusters:** emit an entity cluster only when ≥ 2 of its members appear inside the same tender. That single condition is what keeps output auditable instead of a hairball.\n- **Exclusion masks:** subtract known duplicate groups before splitting analysis; the two detectors must not report the same rows.\n\n**Joins and reference tables**\n- **Broadcast-hash-join small reference tables** (Schedule of Rates ~tens of thousands of rows, GST rate tables, threshold ladders) into the fact table and compute deviation as pure column arithmetic — no grouping for the absolute test.\n- **Compiled regex with token alternation** applied as a vectorised `str.contains` for coded-filename families; one compiled pattern, not a Python loop.\n- **Exact hash join on identifiers when they exist; fuzzy never promoted to the same evidence class.** An exact-PAN hit and a fuzzy-name hit must land in different tiers of the evidence hierarchy — the matcher in `src/stage8/matching.py` already supplies the tiering; use it rather than flattening.\n\n**Scale note:** at 1M rows every detector above is one global sort plus streaming passes. Nothing here materialises an n² object; the only quadratic work is inside size-capped candidate windows.\n\n---\n\n## 4. What NOT to build\n\nA plan that only adds work is worth less than one that also cancels it. Each of these is implementable today and should be explicitly **not** implemented.\n\n**Do not build a fuzzy `vendor_name` entity resolver and call it entity resolution.** With no PAN, no CIN, no address, no DOB, and code-mixed Hindi/English strings, the ARACHNE guidance says the fuzzy matcher degrades badly — and this is the worst case for it. A name-only cluster manufactures false conflict-of-interest claims in an evidentiary product. Exact normalised equality only.\n\n**Do not name-match against the CPPP debarment list.** `src/stage8/typology.py`'s own `verification_note` on `DEBARRED_ENTITY` already says this. Matching a debarment register on name similarity is not a weaker version of the real test — it is a defamation risk with a different failure mode.\n\n**Do not build the vendor × agency × district co-occurrence graph.** Its two useful reads — vendor concentration and repeated vendor-agency pairing — are already covered by the built HHI. It would ship a graph visualisation that adds no signal. (R4's *sequence* test is exempt because order is not recoverable from shares; concentration and pairing are.)\n\n**Do not use `amount_spent / sanction_amount` as a bid-to-reference price ratio.** It is not that quantity. Feeding it into a BRIAS-shaped weighted score means computing a three-input index from one degraded input — the arithmetic runs and the number means nothing.\n\n**Do not re-report cost overrun as a new detector.** `spend_ratio` is already one of the three `PEER_STAT_FIELDS` and already carries a z-score. `amount_spent > sanction_amount` is the same signal with a threshold on it.\n\n**Do not rebuild temporal-ordering checks.** `src/stage2/temporal.py` and the `work_before_approval` compliance rule already cover date inversions, and `compute_duration_days` already refuses to emit a duration where Stage 2 recorded a hard fail. Adding a second date-sanity layer creates two components disagreeing about the same rows.\n\n**Do not build the attentional cascade classifier.** Only its *shape* transfers without labels, and PARAKH already has that shape as confidence gate → severity → routing. The per-stage boosted classifier and the negative re-mining loop are label-bound.\n\n**Do not generate pseudo-labels, weak labels, or synthetic fraud labels to enable supervised learning.** With zero real positives, a model trained on injected defects learns the generator, and its scores would enter an evidentiary product wearing the authority of a trained classifier. The injection ledger validates detector *machinery*; it is not a fraud target and must never be used as one.\n\n**Do not hard-code ₹25 lakh as the sole splitting threshold.** Measured: 5.9% coverage on the dev corpus. Use the cited per-state, per-period ladder, and let the density test find thresholds the ladder misses.
